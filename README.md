# WorkBuddy 用量实时看板

一个**纯本地**的 WorkBuddy token / 积分消耗看板。直接读本机会话记录，实时增量刷新，
细到 **账号 → 设备 → 项目 → 会话 → 轮次 → 单次 API 请求**，并且能分清**模型**与**档位**。

只监听本机回环地址，不联网、不上传、不写任何 WorkBuddy 的文件。

---

## 快速开始

**方式一（推荐）：桌面快捷方式**

桌面上有一个 **「WorkBuddy 用量看板」**，图标是蓝底上升三柱。双击即可：

1. 已在运行 → 直接打开浏览器，不会再起第二个进程
2. 没在运行 → **后台隐藏窗口**启动（不会闪出 cmd 黑框）
3. 启动后轮询探测，确认服务真的应答了才打开浏览器
4. 起不来 → 弹窗给出排查指引，并把日志路径写清楚（不会"双击没反应"）

快捷方式丢了或换了目录，重新生成：

```bash
python tools/create_shortcut.py
```

**方式二：`start.bat`**（想看实时日志时用，会保留一个命令行窗口）
**方式三：命令行**

```bash
python server.py                  # 默认 8791，自动多地址绑定
python server.py --port 8899 --open
python server.py --probe          # 探测是否在跑（退出码 0=在跑）
python server.py --stop           # 停止正在运行的看板
python server.py --diagnose       # 启动失败时弹窗给出排查指引
python server.py --lan            # 额外在局域网开放（见下方安全提示）
```

停止看板：双击 `stop.bat`，或 `python server.py --stop`。

无第三方依赖，Python 3.8+ 标准库即可。日志写在 `dashboard.log`，pid 写在 `dashboard.pid`。

## 它能回答什么

它**默认按积分（真正计费的口径）统计**，顶栏一个开关可以切到 Tokens。
切换后 KPI、分布图、排行榜、默认排序、表格里高亮的那一列会全部跟着变；
口径也会写进 URL（`?metric=tokens`），所以视图可分享、刷新不丢。

| 问题 | 看哪里 |
| --- | --- |
| **今天 / 这周烧了多少积分** | 总览 KPI 第一张卡；分布图上方右对齐的合计行 |
| 平均一轮提问、平均一次请求花多少积分 | KPI 的「平均每轮积分」「平均每请求积分」 |
| **消耗按模型/项目/会话怎么分布、逐日怎么走** | 总览「每日消耗分布」：柱=按当前维度拆开，线=当日合计 |
| 哪个项目 / 会话 / 轮次最费积分 | 项目排行、会话排行、轮次明细（默认按积分降序，积分列高亮） |
| 哪个模型最费积分 | 模型排行 + 模型与档位 |
| **同一档位实际跑在哪个模型上，各占多少积分** | 模型与档位 → 「档位 → 实际承载模型」，占比按当前口径算 |
| **某一天里几点最烧** | 24 小时分布 → 右上角选日期（默认全部日期合计） |
| **每一轮各花了多少** | 轮次明细页顶部「轮次分布图」：一轮一根柱 + 7 轮均线 |
| 消耗多是因为用量大还是因为单价高 | 切到 Tokens 对照：两个口径的排序往往不一样（举例：某模型按积分占 39%，按 Tokens 只占 27%，另一个模型正好反过来） |
| 一次提问里 52 次请求分别是谁花的 | 轮次明细 → 展开 → 逐请求表 |
| 缓存到底省了多少 | 缓存命中率 + 每轮/每请求的缓存命中列 |

### 只有一张分布图（柱+线）

总览页的「**每日消耗分布**」把原来的「每日消耗」与「按维度分布」合成了同一张图：

- **柱** = 按当前维度（模型 / 项目 / 会话）拆开的每日消耗，**只画前 5 名**（图例也只列这 5 个），
  颜色与图例一一对应；
- **线** = **每个横轴单位**的合计（这组柱的总和），拆开看的同时不丢整体走势；
- **口径跟着顶栏的 积分 / Tokens 按钮走** —— 整张图（柱和线）都是同一个口径。
  不固定成"一条积分一条 Tokens"：那两个量级差 6 个数量级，硬塞进一张图里刻度没有意义。

轮次明细页的「轮次分布图」同理：柱=每一轮（按维度着色），线=7 轮滑动平均
（几百根柱太密，只有均线能看出趋势；同样只列前 5 名）。表格保留在下方。

#### 颜色即重点

之前的问题是**最该被看见的那条线是黑的**，和满屏黑字混在一起分不出重点。现在：

- **「积分=橙 / Tokens=蓝」这两个颜色是语义色**，只留给**合计折线**（画粗到 3.2px，点也加大）；
- **柱子的配色刻意避开橙和蓝**（青/紫/绿/粉/黄绿），所以线永远是最跳的那一条；
- **总计单独放在图上方右对齐**（不在图例里），标签按粒度走：`所选范围合计 / 该月合计 / 该周合计 / 该日合计`，
  数值和短横线也用同一个语义色 —— 它代表那条折线，不是"某一天"的合计；
- 坐标轴文字从浅灰提到 `--muted` 并加大到 14px —— 之前是 11.5px 浅灰，根本看不清。

#### 字号

正文 16.5px，表格 15px，图表轴标签 14px，图例 15px，KPI 数字 27px，主角卡 46px。
13 列的表格在窄屏下会横向溢出，这时标题旁会出现「← 可左右滚动 →」的提示
（不提示的话容易被当成内容缺失）。

### 可切换的视图状态

三处开关**都会写进 URL**（形如 `?metric=tokens&dim=session&day=2026-09-14`），
任何一屏都能直接分享，刷新也不会丢：

| 开关 | 位置 | 作用 |
| --- | --- | --- |
| 积分 / Tokens | 顶栏 | **全局口径**：KPI、分布图、排行、默认排序、高亮那列全跟着走 |
| 全部 / 按月 / 按周 / 按日 | 每日消耗分布 卡右上 | **粒度下钻**：全部=逐日；按月/按周=选定周期内逐日；按日=逐**小时** |
| 年-月 / 周一日期 / 日期 下拉 | 紧跟粒度开关 | **共用一个下拉位置**，选项随粒度切换；选中的周期决定横轴范围 |
| 模型 / 项目 / 会话 | 每日消耗分布 卡右上 | 柱按哪个维度拆。与轮次分布图**共用同一个维度**，改动会同步 |
| 日期下拉 | 24 小时分布卡右上 | 只看某一天的 24 小时分布，或看全部日期合计（全期聚合，与上面的"按日"互补） |

粒度是**层层下钻**的：`全部` 看整体走势 → `按月` 锁定某月 → `按周` 锁定某周 → `按日` 下到小时。
越往下钻，横轴越细（天 → 小时），柱和合计线同时跟着变。

> 页面顺序：**额度条 → KPI → 筛选 → 标签页 → 图表**。
> 数字放前面、筛选放后面——先看到结论，再决定要不要筛。

同一份数据在两个口径下的排序**经常不一样**，这正是要留两个口径的原因：
比如某个项目 Tokens 最多，但积分最高的却是另一个项目 —— 用量大不等于烧得多，
因为不同模型的单价差得很远。

## 本周期已消耗 / 剩余积分

看板顶部有一条**账户级的额度条**，右边的「设置」就是填数的地方：

```
[2026-01]  本周期（01-05 ~ 02-04）已消耗 3200 积分   剩余 6800 / 10000 积分  ▓▓▓▓▓▓░░░░
           周期内还剩 20 天 · 日均可用 340                                    [设置]
```

点「设置」展开三个输入框，填完点保存（**写入 `config.local.json` 的 `quota` 段，只在本机**）：

| 字段 | 填什么 |
| --- | --- |
| 每月套餐额度 | 你的套餐每月给多少积分 |
| 当前剩余 | **去官方用量页看到的那个数字** |
| 每月刷新日 | 套餐每月几号刷新（1-31） |

### 剩余是怎么算的（你只填一次，之后自动）

优先级从高到低：

1. **填过「当前剩余」且还在本周期内** →
   `剩余 = 你填的数 − 之后新增的消耗`。
   保存那刻记下基准点，之后每来一笔消耗自动扣减，**不用你天天改**。
   （举例：昨天填 5000，期间消耗了 1200 → 自动算出剩余 3800，不用你天天改）
2. **只填了套餐额度** → `剩余 = 套餐额度 − 本周期已消耗`。
3. **都没填** → 显示「额度未设置」，只有本机记录的消耗。

到了刷新日（下一个周期开始），上次那份剩余量就过期了，看板会**明确提示你更新一次**，
并在你更新前先回落到按套餐额度推算，不会拿旧数据糊弄你。

> **关于口径差异**：本机记录的消耗 和「额度−剩余」隐含的消耗经常对不上
> （可能有别处的消耗，或计费口径不同）。看板会把这个差异直接写出来，
> 并且**一律以你填的剩余为准**——毕竟那才是官方的数。

> 这条是**账户级**数字，**不随上面的筛选条件变化**。要是跟着"项目/日期"筛选变，
> 算出来的"剩余"必然是错的，所以它单独放在筛选区之上。

## 图标：一处定义，三处使用

同一个图形（**绿色圆角方块 + 三根渐次升高的柱**）用在三个地方：

| 用在哪 | 来自 | 怎么生成 |
| --- | --- | --- |
| 桌面快捷方式 | `icon.ico`（7 种尺寸） | `python tools/make_icon.py`（纯 Python 光栅化，不依赖 Pillow/浏览器） |
| 标签页图标 | `static/favicon.svg` | 手写的矢量版，**几何参数与 make_icon.py 逐一对齐** |
| 页面左上角 | 同上（`<img src="/static/favicon.svg">`） | 引用同一份文件，不另画 |

**关键约束**：`favicon.svg` 的坐标和 `make_icon.py` 里的常量必须一致，
改色只动颜色、别动坐标 —— 否则快捷方式图标和网页图标会慢慢长得不一样。
两边的颜色都是 **`#0ec8a9 → #16cb82`**，柱子的透明度是同一组 `0.70 / 0.86 / 1.0`。

### 绿色是"采样"来的，不是配出来的

想贴近 WorkBuddy 官方图标的绿，凭眼睛调很容易差一截。所以写了 `tools/sample_icon.py`：
把官方 `WorkBuddy.exe` 的图标抽出来（`PrivateExtractIconsW` → `GetIconInfo` → `GetDIBits`）
读真实像素，沿竖中线采样，直接拿到渐变两端：

| | 官方 WorkBuddy | 本看板 |
| --- | --- | --- |
| 顶部 | `#0ec8a9` rgb(14,200,169) | `#0ec8a9` ✓ |
| 底部 | `#16cb82` rgb(22,203,130) | `#16cb83`（差 1/255，取整） |

顺带发现一个容易搞错的点：**官方是"色相"渐变（青绿→绿），不是明暗渐变**。
我第一版按"上亮下深"配的（`#4ade80 → #15803d`）所以看着不对 ——
这种差别肉眼说不太清，但采样一量就出来了。

`python tools/compare_icons.py` 会把两个图标抽出来拼成一张并排对比图（`tools/icon_compare.png`），
人和脚本都能直接看/量。

### 踩过的坑：图标不显示

标签页图标要**两个条件同时成立**，缺一个就只能显示浏览器默认的灰色地球：

1. **HTML 里要有 `<link rel="icon">`** —— 之前根本没有这个标签；
2. **服务端要能返回它** —— 之前只路由 `/` 与 `/static/*`，
   而浏览器在找不到声明时会**默认去请求 `/favicon.ico`**，那条路径 404。

两条都补齐后：`favicon.svg` 走 `/static/`，`/favicon.ico` 由服务端映射到根目录那个多尺寸 ico
（给不支持 SVG 图标的兜底），另加 `apple-touch-icon`。

### 图标缓存：现在会自动失效

favicon 是**独立于 HTTP 缓存**的一套，极其顽固 —— 本项目被它坑过两次：
先是"根本没有图标"（HTML 没声明 + 服务端没路由），后来是"改了图标但标签页还显示旧的蓝色 WB"。

所以首页不再直接输出 `<link rel="icon" href="/static/favicon.svg">`，而是带一个版本号：

```
<link rel="icon" href="/static/favicon.svg?v=1789488651">
```

服务端渲染首页时把 `__ICON_V__` 替换成 **图标文件的 mtime**。于是：

- 改图标（或 `touch` 一下）→ URL 立刻变 → 客户端当成新资源重新拉 → **缓存必然失效**；
- 不用手动维护版本号，不会忘。

实测：`touch static/favicon.svg` 后，首页里的版本号从 `…651` 变成 `…986`。

> **已经开着的标签页仍要重新加载一次**（标签图标是页面加载时取的），
> 必要时关掉标签页重开。WorkBuddy 内置浏览器同理。
> Windows 桌面图标也有缓存 —— 快捷方式已指向新的 `icon.ico`，
> 桌面按 **F5**（或重启资源管理器）即可。

## 页面层级是怎么设计的

**关于「轮次」的定义**：一次用户提问 → 下一次提问之间的所有 API 请求算一轮。
之所以不用 `conversationRequestId` 分组：实测它和提问数并不相等（一条提问可能对应多个
convReq，也可能是系统补发），按提问时间轴切分才是用户认知里的「一轮」。

轮次会按来源打标，避免把系统消息误当成你的提问：

| 标签 | 含义 |
| --- | --- |
| `提问` | 你自己发的消息 |
| `后台通知` | `<task-notification>`：后台任务完成通知（占比不低，别把它当成自己发的提问） |
| `自动压缩` | 上下文超限时系统自动压缩产生的轮次 |
| `自动续跑` | 压缩后系统自动续跑 |
| `命令` | 斜杠命令 |
| `后台任务` | 没有对应用户提问的请求（标题生成、Prompt 预测等） |

## 数据来源与字段映射

数据源：`~/.workbuddy/projects/<项目>/<sessionId>.jsonl`
**增量读取**——按字节偏移只读新增部分，不整文件重扫，所以 2 秒一轮的实时刷新也很轻。

| 记录位置 | 用途 |
| --- | --- |
| `providerData.usage.{inputTokens,outputTokens,totalTokens}` | 输入 / 输出 / 合计 tokens |
| `providerData.usage.inputTokensDetails[0].cached_tokens` | 缓存命中 tokens |
| `providerData.usage.outputTokensDetails[0].reasoning_tokens` | 思考 tokens |
| `providerData.rawUsage.credit` | **本次请求消耗的积分**（0 = 该模型不计费） |
| `providerData.rawUsage.prompt_cache_hit_tokens / miss` | 缓存命中 / 未命中 |
| `providerData.model` | **实际承载推理的模型 id**（计费口径） |
| `providerData.requestModelId` | **档位 / 场景**：`balanced-model`＝均衡（自动档）、`fast-model`＝快速（自动档）、其余即指定模型 |
| `providerData.requestModelName` | 展示名。⚠️ 有时填的是**档位名**而不是模型名，不能直接当模型名用 |
| 顶层 `timestamp` / `sessionId` / `cwd` | 时间 / 会话 / 项目目录 |
| `type == "ai-title"` 的 `aiTitle` | 会话标题。同一会话会有**多条**（改名/改题会追加），必须**按时间戳取最新**，不能按文件顺序取最后一条 |

**去重**：按 `providerData.messageId`，实测全球唯一，直接逐条累加即可。
（`traceId` 是「一轮」级别、`conversationRequestId` 也会重复，都不能用来数请求。）

**用户提问的提取有个坑**：提问常被包在 `<system-reminder>…</system-reminder>` 里
（比如会话第一条消息），真实提问在同一消息的后半段。整条丢掉会导致**每个会话的第一条提问消失**，
必须先把注入块剥掉、再去匹配 `<user_query>…</user_query>`。

## 账号与设备的归属：请先读这段

会话记录里**不含**逐请求的账号/设备字段。本看板的归属方式是按**安装实例**：

- **账号** ← `settings.json` 的 `claw.users` 键 + `connectors/*/connector-states.json` 的
  `accountIdentityKey`（形如 `<uuid>||enterprise`）。看板顶部会把它标出来。
- **设备** ← `~/.workbuddy/device-id` + 主机名，客户端版本 ← `last-launch.json`，
  会话级主机名 ← `~/.workbuddy/sessions/<pid>.json`。

也就是说：**同一台机器上这个 WorkBuddy 安装产生的所有消耗，都归到这个账号 + 这台设备**。
如果你有多账号/多设备，只要它们的 `~/.workbuddy` 在同一台机器上被分别启动过，
本看板会按实际落盘的标识分开显示；但**不要**把它理解成"官方账单级别的逐请求归属"。
页面上也写了这条说明，不做假精确。

如果官方后续在会话记录里补上逐请求账号字段，改 `resolve_identity()` 和 `_ingest_line()` 即可。

## 接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/meta` | 账号、设备、项目、会话、模型、档位、总计数 |
| POST | `/api/config` | 保存额度设置（套餐额度 / 当前剩余 / 刷新日）→ 写 `config.local.json` 的 `quota` 段 |
| GET | `/api/config` | 读回当前额度设置 |
| GET | `/` | 首页（渲染时把 `__ICON_V__` 换成图标文件 mtime，用于图标缓存失效） |
| GET | `/api/hourly` | `?day=YYYY-MM-DD` → 该日**按小时**×三维度的分布（粒度下钻到"按日"时用） |
| GET | `/api/whoami` | 极小响应，返回自己的 pid（`--probe` / `--stop` 用，不依赖 pid 文件） |
| GET | `/api/summary` | 总览聚合：总量、按天、按小时、**按天的小时分布**、**三维度逐日曲线**、**本月用量与剩余额度**、按模型/档位/项目/会话，含档位→实际模型对照 |
| GET | `/api/turns` | 轮次明细（分页、可排序） |
| GET | `/api/turn?id=<turnId>` | 某一轮的逐请求明细 |
| GET | `/api/export.csv` | 轮次级 CSV（带 BOM，Excel 直接打开） |
| GET | `/api/stream` | SSE 实时推送（默认 2 秒扫一次，有变化才推） |

筛选参数（`/api/summary`、`/api/turns`、`/api/export.csv` 通用）：
`from`、`to`（YYYY-MM-DD）、`project`、`session`、`model`、`scene`、`q`（关键词，命中**轮**而不是整个会话）。

页面 URL 用 hash 记录当前标签（`#overview` / `#turns` / `#sessions` / `#models`），可分享、刷新不丢。
`?nolive=1` 关闭实时推送。

## 页面层级是怎么设计的

仪表盘最容易犯的错是"所有数字一样大"——看着信息很多，其实一个也记不住。这里做了明确分层：

1. **唯一的主角卡**（贯穿整行）：当前口径的主指标用 42px 大字，配一条推导信息
   （平均每轮 / 平均每请求），右边用分隔线隔出**另一口径**做对照。一屏只有一个视觉焦点。
2. **支撑卡**（小卡一排）：缓存命中率、输入/输出/思考 Tokens、平均每轮。
   **数字与单位分开渲染**——同字号下「亿 / 万」这类中文字形的视觉高度接近整个 em 框，
   比拉丁数字显得大一大截，23px 下会像排版坏了。所以数字 23px、单位 13.5px，
   副值独占一行并置灰。
3. **排行榜带占比**：只给绝对值很难判断大小关系，加上占总量百分比后
   一眼就能看出"3 个模型吃掉了 99% 的积分"。
4. **并排卡片等高**：24 小时分布卡用 flex 撑满整行高度，图跟着卡片长高
   （改前卡高 390 / 图高 106 / 下方空 225px；改后图高 314、只留正常内边距 17px）。
5. 次要信息（账号/设备归属说明、数据来源）压在页脚，不占首屏。
   顶栏徽标只留必要内容，原始 UUID 收进 tooltip。

配色即语义：**积分 = 橙（--amber）、Tokens = 蓝（--blue）**，
切换开关、主图、排行条、表格里高亮的那一列全部用同一套颜色，不用再找图例。

## 已知限制

1. **逐请求的账号/设备归属不存在**（见上一节）——按安装实例归属。
2. **回环地址的可靠性因环境而异**：某些网络加速 / 防护软件可能拦截 `127.0.0.1` 的连接，
   表现为「端口在 LISTENING，但谁也连不上（超时）」，而 `::1` 不受影响。
   所以服务**启动时会真的连一次自己**，把每个绑定地址标 ✓/✗，并优先用可用的那个 ——
   而不是"起来了就算成功"。
3. `0.0.0.0`（LAN）可用，但**默认不开**，见下方安全提示。
4. 会话 jsonl 是**实时追加**的，两次刷新数字可能差几条请求，这是真实增长，不是统计错误。
5. 单机几天的会话记录（数千次请求）规模下，全量索引约 1 秒、单次聚合查询约 0.2 秒。
   数据量再大一个量级时建议给 `build_summary` 加缓存（当前只缓存了轮次切分结果）。

## 你的数据放在哪（脱敏设计）

会话记录本身就是个人数据（提问原文、项目路径、命令文本），额度和会话名同样是。
所以这个仓库按「**代码公开、数据本地**」组织：

| 内容 | 存在哪 | 会不会进仓库 |
| --- | --- | --- |
| 套餐额度 / 当前剩余 / 刷新日 | `config.local.json` → `quota` | 不会 |
| 手写会话名 | `config.local.json` → `sessionTitles` | 不会 |
| 运行日志 / pid | `dashboard.log` / `dashboard.pid` | 不会 |
| **账号标识**（账号 UUID、`accountIdentityKey`） | 运行时从 `~/.workbuddy/settings.json`、`connectors/*/connector-states.json` 现读 | 不会 |
| **设备标识**（设备 UUID、主机名） | 运行时从 `~/.workbuddy/device-id` + `socket.gethostname()` 现读 | 不会 |
| **本机记忆**（AI 协作产生的项目笔记、会话日志） | `.workbuddy/`、`~/.workbuddy/memory/` | 不会 |
| 会话记录本身 | `~/.workbuddy/projects/**/*.jsonl`（只读，不复制） | 不会 |

> **关于账号与设备标识**：仓库里只有**读取它们的代码**，没有任何一个真实值 ——
> 账号 UUID 和设备 UUID 都是运行时从本机文件读出来的。README 这一节描述的是
> 「归属是怎么算的」，不是在公布某个账号是谁。

四件事保证不漏：

1. **个人数据集中在一个文件** —— `config.local.json`。散在多个文件里迟早漏一个，
   集中之后只要挡住一个名字就够了。
2. **`.gitignore` 挡住它**，并且旧文件名（`quota.json` / `session-titles.json`）、
   本机记忆目录（`.workbuddy/`、`**/memory/`）、会话记录（`*.jsonl`）、
   身份文件（`device-id`）也一并挡住 —— 防止哪天被复制进项目目录再被误加。
3. **启动器不写死绝对路径** —— Python 解释器是启动时探测的：
   先找 `%USERPROFILE%\.workbuddy\binaries\python\versions\*\python.exe`，
   找不到再回退 PATH 里的 `python`。写死路径等于把用户名带进仓库，而且对别人必然跑不起来。
4. **提交前有脚本把关**（见下）—— 不靠人记得检查。

**克隆这个仓库的人**：`cp config.example.json config.local.json` 再按需改；
不改也能跑，只是没有额度数据和手写会话名。`config.local.json` 从来不会被提交。

### 提交前自查：一次命令扫干净

```bash
python tools/check_personal.py            # 工作区 + 已跟踪文件（日常提交前跑）
python tools/check_personal.py --staged   # 只查暂存区
python tools/check_personal.py --history  # 连全部 git 历史一起查（开源/发布前跑一次）
```

它会从**本机**读出身份标识（家目录路径、用户名、主机名、账号 UUID、设备 UUID），
拿它们反查仓库，并确认那几个本地数据文件确实被忽略了。退出码 0 = 干净，1 = 有东西要处理。

两个细节：

- 脚本打印标识时**只显示前 6 位和长度** —— 否则「自查工具的输出」本身就成了新的泄漏点；
- 脚本里**不写任何真实标识**，全部运行时读取，所以它可以安全地公开。

想让它自动跑，装个提交钩子：

```sh
printf '#!/bin/sh\nexec python tools/check_personal.py --staged\n' > .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit
```

> 注意钩子只拦「新增的提交」。如果敏感内容**已经推送过**，
> 删文件是没用的 —— blob 还留在历史里，得用 `git filter-repo` 重写历史，
> 并把泄漏过的凭据作废轮换。

## 安全提示

看板会展示**提问原文、项目路径、命令文本**（`<task-notification>` 的摘要里可能带命令参数，
其中可能含 token 片段）。所以：

- 默认**只监听回环**，别改成监听公网。
- `--lan` 会让同网段的任何设备都能读到这些内容，**只在完全可信的内网里用**。
- 本工具不写 WorkBuddy 的任何文件，只读。
